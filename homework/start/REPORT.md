# REPORT.md

## Результат

Реализованы требования R1, R2 и R3. Дополнительно обработан символ нулевой ширины U+200B.

Итоговая проверка:
- 12 тестов пройдены.
- `npm run build` завершился успешно.
- Изменения реализации находятся в `src/tasks.ts` и `src/App.tsx`.
- Результаты проверок сохранены в `evidence/red.txt`.

## Анализ сбоев

### Planning
Работа была разделена на спецификацию, тесты, реализацию и проверку. Изолированная копия для агента намеренно не содержала тестов, поэтому проверка `npm test` в ней не могла пройти.

### Context
Агент получил SPEC.md, но не тестовый файл. Это было сделано намеренно, чтобы агент не видел тесты. Проверка реализации выполнялась отдельно в основном проекте.

### Tool
Первая попытка выполнить red run (b) не состоялась: код TypeScript был введён в PowerShell вместо редактора. Эта попытка не учитывалась как успешный red run. Позже проверка была выполнена корректно.

### Policy
Нарушений ограничений на изменяемые файлы и зависимости в итоговой реализации не обнаружено. Тесты не передавались агенту.

### Artifact
Проверки выявили следующие дефекты:
- создание задачи не обрезало пробелы по краям;
- переименование не отклоняло пустое название;
- доска показывала унаследованные пустые задачи;
- счётчик открытых задач учитывал пустые задачи;
- стандартный trim() не обрабатывал U+200B.

### Verification
Результаты red runs:
- (a): 1 тест упал, 9 прошли — обнаружено отсутствие обрезания названия при создании;
- (b): 5 тестов упали, 5 прошли — обнаружено отсутствие проверки при переименовании;
- (c): 2 теста упали, 8 прошли — обнаружено отображение пустых задач;
- (d): 2 теста упали, 10 прошли — обнаружена неправильная обработка U+200B.

После исправлений: 12 из 12 тестов прошли, production-сборка успешна.

### UX
Ручной поиск мест для изменения кода оказался неудобным. Изменения тестов, спецификации и реализации в итоге были автоматизированы PowerShell-скриптом.

### Recovery
После red runs (b) и (c) рабочая реализация восстанавливалась из резервной копии. После добавления поддержки U+200B резервная копия была обновлена.

## Evidence

## Generalizable rule

Для каждого требования нужно иметь отдельный проверяемый acceptance test. Полезно проверять не только успешную реализацию, но и то, что тест действительно падает при удалении соответствующей проверки или фильтра. После каждого отрицательного эксперимента нужно восстанавливать рабочую реализацию и повторно запускать весь набор тестов.
